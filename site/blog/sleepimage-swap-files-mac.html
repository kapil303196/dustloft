sleepimage, swap files and /Library/Updates: System Data to leave alone

Guide · 5 min read · By Kapil Upadhyay at Logicspark · Published 8 November 2026

Short answer: leave all three alone. sleepimage is recreated the next time the Mac sleeps, swap files disappear on a restart, and /Library/Updates is protected by System Integrity Protection, so even sudo rm fails there. Restarting and installing or dismissing the pending update are the supported ways to shrink them.

Search for ways to shrink System Data and these three paths come up constantly, often with a sudo rm attached. All three are real consumers of space, and none of them is worth deleting by hand. The figures below are from a 512 GB MacBook Pro (Mac16,8, 24 GB memory) running macOS 26.5.1, measured on 8 November 2026.

sleepimage

ls -lh /private/var/vm/
pmset -g | grep -E 'hibernatemode|hibernatefile'

On this Mac the file was 2.0 GB, with hibernatemode 3, the laptop default: memory stays powered while asleep, and is also written to sleepimage so nothing is lost if the battery dies. Note that it was 2.0 GB on a machine with 24 GB of memory, so the old rule that the file matches your RAM does not hold on Apple silicon.

Deleting it gains nothing: macOS writes a new one the next time the Mac sleeps. The only way to stop it is sudo pmset -a hibernatemode 0, which means a Mac that runs flat while asleep loses everything that was open. For 2 GB, that is not a good trade on a laptop.

Swap files

sysctl vm.swapusage
ls -lh /System/Volumes/VM

macOS keeps swap on its own APFS volume, /System/Volumes/VM, not in /private/var/vm as older guides say. On this Mac, vm.swapusage reported total = 0.00M and the volume was empty. Under memory pressure — a browser with hundreds of tabs, several Docker containers, a local AI model — swap can grow to many gigabytes. It is released when the pressure goes and cleared entirely on a restart. If swap is consistently large, quitting the application that is using the memory is the fix, not deleting the files.

/Library/Updates

du -sh /Library/Updates/*
ls -ldO /Library/Updates

On this Mac the folder held 2.0 GB across four update packages, two of them 899 MB each. The second command shows the folder flagged restricted: it is protected by System Integrity Protection, which was enabled here, as it should be. Even an administrator cannot delete from it. That is deliberate — a half-deleted update is how a Mac ends up refusing to install the next one.

The supported fix is to let the update finish. Install it from System Settings › General › Software Update, and macOS clears the staged files afterwards. If you have decided not to install a particular update, the downloaded files are removed when a newer update replaces it.

What to do instead

These three together came to about 4 GB on this Mac. On the same disk, ~/Library/Application Support held 30 GB and ~/Library/Caches held 12 GB. If System Data is large, the space is almost always in your home folder, and the step-by-step guide shows how to find it.

Common questions

Can I delete sleepimage on a Mac?

You can, but macOS recreates it the next time the Mac sleeps, so nothing is gained. Stopping it needs hibernatemode 0, which loses open work if the battery runs out while the Mac is asleep.

Where are swap files on macOS?

On their own APFS volume mounted at /System/Volumes/VM. sysctl vm.swapusage shows how much is in use. A restart clears them.

Can I delete /Library/Updates?

No. The folder is protected by System Integrity Protection, so even sudo cannot remove files from it. Installing the pending update is what clears it.

Does restarting a Mac reduce System Data?

A little. A restart clears swap files and some temporary files, which can free a few gigabytes on a Mac that has been under memory pressure. It does not touch caches, app data, backups or snapshots.
